# What is Telemetry

**Telemetry** literally means "measurement from a distance" &rarr; the same word used for the data a spacecraft radios back to mission control, or the readouts a race car streams to its pit crew mid-lap. In FRC, it means the same thing: numbers, states, and events generated by code running on the roboRIO, sent somewhere a human (or a file) can actually look at them.

Without telemetry, the robot is a black box. It's running code, reading sensors, driving motors &rarr; but you have no way to know *what it's actually doing* unless you can watch it happen. Every one of our subsystems, utility classes, and state machines is constantly producing telemetry, whether or not anyone is watching at that exact moment.

---

## Logged vs. Live: Two Kinds of Telemetry

Not all telemetry is used the same way. It's worth splitting it into two categories before looking at examples:

- **Live telemetry** &rarr; data sent out *right now*, for a human or dashboard to see in the moment. A battery voltage reading on the driver station,the  rpm of a flywheel, a live graph of a PID error: all only useful *while the robot is running*.
- **Logged telemetry** &rarr; data saved to a file so it can be looked at *after the fact*. A full match's worth of motor currents, pose estimates, and state transitions, written to a `.wpilog` file, so you can go back after a match and figure out exactly what happened, frame by frame.

<Note title="These aren't mutually exclusive">
The same piece of data is very often both at once. When our code calls `Logger.recordOutput(...)`, that value gets written to a log file *and* published live so it shows up on a dashboard immediately &rarr; you'll see exactly how in the next page of this section.
</Note>

## What Actually Gets Recorded

"Telemetry" isn't one specific thing &rarr; it's a category that covers several very different kinds of data. Our codebase already has a component built for each kind. Here's a tour of the actual telemetry sources in `Rebuilt2026`:

### Raw Hardware & Sensor State

The most basic form of telemetry is just: *what is a piece of hardware currently reporting?* Every subsystem in our codebase follows an **IO pattern** &rarr; a small class (like `FlywheelIOInputs`) that holds every sensor reading for that subsystem, marked with an `@AutoLog` annotation:

```java
public interface FlywheelIO {
    @AutoLog
    class FlywheelIOInputs {
        public boolean leftConnected = false;
        public double leftPositionRad = 0.0;
        public double leftVelocityRadPerSec = 0.0;
        public double leftAppliedVolts = 0.0;
        public double leftSupplyCurrentAmps = 0.0;
        public double leftTempCelsius = 0.0;
        // ... right motor fields
    }
}
```

Every loop, the subsystem fills this object in from the actual motor controller, and every field gets recorded automatically &rarr; this is raw, unprocessed telemetry, straight from the hardware.

### Computed & Derived State

Not all telemetry comes straight off a sensor &mdash; a lot of it is *computed*: a decision the code made, or a state it transitioned into. This is logged manually with `Logger.recordOutput(...)`, or automatically off a field with `@AutoLogOutput`:

```java
// RobotState.java
public void setAimState(AimState mode) {
    Logger.recordOutput("AimState/ModeChange", currentAimState.name() + " -> " + mode.name());
    Logger.recordOutput("AimState/CurrentMode", mode.name());
}
```

```java
// RobotState.java
@AutoLogOutput
private final Trigger nearHubTrigger;
```

This kind of telemetry answers a different question than raw sensor data: not "what did the encoder read," but "what did the robot's code *decide* based on that reading."

### Performance Metrics

Telemetry doesn't only describe the robot's mechanisms &rarr; it can describe the *code itself*. `LoopTimeUtil` and `BatteryUtil` (covered in an earlier section) exist purely to generate telemetry about how the robot's own software and power system are behaving:

```java
// LoopTimeUtil.java
Logger.recordOutput("LoopTimes/" + subsystem + "ms", (now - startTime) * 1000.0);
```

```java
// BatteryUtil.java
Logger.recordOutput("BatteryUtil/TotalCurrentDraw", loopTotalCurrent);
```

<Note title="Why this counts as telemetry too">
It's easy to think of telemetry as only "robot sensor data," but a loop taking too long or a battery sagging under load is just as important to observe as an encoder reading &mdash; arguably more so, since a loop overrun or a brownout can break *everything else* the robot is doing.
</Note>

### Tunable & Configurable Values

Some telemetry flows the *other* direction &rarr; not the robot reporting to a human, but a human adjusting a value on the robot live. `LoggedTunableNumber` and `Toggles` (both covered in the Util section) publish a value out, and read back whatever a human set it to:

```java
// Hood.java
kP = new LoggedTunableNumber("Hood/kP", constants.kP());
```

```java
// Toggles.java
LoggedNetworkBoolean tuningMode = new LoggedNetworkBoolean("Toggles/TuningMode", false);
```

<Note title="New term: two-way telemetry">
Most telemetry is one-directional (robot to human) `LoggedTunableNumber` and `Toggles` are a good example of telemetry flowing *both* ways over the same channel: the robot publishes a default value, and a human overwrites it from the dashboard, and the robot reads that new value back &rarr; all live, without redeploying code.
</Note>

### Visual & Spatial Data

Numbers alone aren't always the clearest way to understand what a mechanism is doing. Our `Visualizer` classes (`IntakeVisualizer`, `SuperstructureVisualizer`, `HoodVisualizer`, `TurretVisualizer`) log a mechanism's current position as a 2D diagram or a 3D pose, so it can be watched moving in real time or replayed after a match:

```java
// IntakeVisualizer.java
public void update() {
    rack.setLength(rackPositionSupplier.get());
    Logger.recordOutput("Intake/Mechanism", mechanism);
    Logger.recordOutput("Intake/ComponentPoses", new Pose3d[] {
        new Pose3d(new Translation3d(...), new Rotation3d())
    });
}
```

This is still telemetry &mdash; it's just visual instead of a plain number on a graph.

### Human-Facing Messages

Finally, some telemetry isn't a number at all &mdash; it's a message meant to be read directly. `Elastic` sends pop-up notifications straight to the dashboard:

```java
Elastic.sendNotification(
    new Elastic.Notification()
        .withLevel(Elastic.Notification.NotificationLevel.WARNING)
        .withTitle("Flywheel Overheating")
        .withDescription("Stator current exceeded safe threshold"));
```

This is telemetry at its most direct: the robot noticed something, and told a human about it in plain language.

## Putting the Categories Together

| Category | Answers the question... | Example Component |
|---|---|---|
| Raw hardware & sensor state | "What is the hardware reporting right now?" | `FlywheelIOInputs` (`@AutoLog`) |
| Computed & derived state | "What did the code decide?" | `RobotState` (`Logger.recordOutput`, `@AutoLogOutput`) |
| Performance metrics | "Is the code itself running properly?" | `LoopTimeUtil`, `BatteryUtil` |
| Tunable & configurable values | "What should this constant be, live?" | `LoggedTunableNumber`, `Toggles` |
| Visual & spatial data | "Where is this mechanism, physically?" | `IntakeVisualizer`, `SuperstructureVisualizer` |
| Human-facing messages | "Does a human need to know this, right now?" | `Elastic` |

Every one of these categories is still telemetry &mdash; they're just different *kinds* of information, flowing for different reasons. What ties them all together is the same underlying idea: **taking something that only exists inside the robot's code, and making it visible outside of it.**

<NoteTabs>
  <NoteTab title="So what carries all of this data around?">
Every single example above ends up going over the same underlying system: **NetworkTables**. That's the actual networking layer that gets a `Logger.recordOutput(...)` call, a `LoggedTunableNumber`, or an `Elastic.sendNotification(...)` call from the roboRIO to a dashboard on the driver station laptop. We'll cover exactly how that works in the next page.
  </NoteTab>
  <NoteTab title="And what actually shows all of this to a human?">
That's the dashboard &mdash; software like Elastic (live, during a match) or AdvantageScope (live, or replaying a saved log after the fact). We'll get to both later in this section too.
  </NoteTab>
</NoteTabs>
